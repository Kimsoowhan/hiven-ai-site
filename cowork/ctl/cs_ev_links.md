# cs_ev_links.tsv 칸 설명 (CS · VOC ↔ 결함 · 시험 · 증적 연결표)

- 만든 때: 2026-11-13. 근거: Fable 지시문 0156 5절 길 1 · 정-9.
- 쓰임: 고객 건(CS)이나 VOC가 시험 사례·결함·증적으로 이어지는 줄과, 거꾸로 시험에서 나온 사건·결함이 고객이 겪을 「알려진 문제」로 이어지는 줄을 한 곳에 둔다.
- 지금 줄 수: 머리 줄 1 · 자료 줄 2(둘 다 알려진 문제, CS 번호 없음). 고객 건 줄 0. 실제 있는 줄만 넣었고 합성·시험 값은 넣지 않는다.
- 빈 칸 규칙: 해당이 없으면 「없음」, 모르면 「확인 안 됨」. 칸을 비워 두지 않는다. 증빙번호 범위가 비어 있으면 precheck가 알린다(정-4 ⓔ).

| 번호 | 칸 | 뜻 · 값 규칙 |
|---|---|---|
| 1 | CS 번호 | cs_tickets.tsv의 CS-세 자리. 알려진 문제 줄은 「없음」 |
| 2 | VOC 번호 | voc_ledger.tsv의 VOC-세 자리, 없으면 「없음」 |
| 3 | 결함 번호 | 결함 대장(SC-13) 번호. SC-13 결함 대장은 모델통제 이력 번호를 그대로 쓴다. 대장에 아직 오르지 않았으면 이력 번호나 판정요청 번호를 쓰고 대장 등재 여부를 괄호로 밝힌다 |
| 4 | 시험 사례 번호 | 사례표의 사례 번호, 사례로 아직 들어가지 않았으면 「없음 · 사례표 미반영」 |
| 5 | 대상ID | 증적 등록부(ev_registry.tsv)의 대상ID. 고객 건 재현은 REPRO-CS-번호 |
| 6 | 실행 일련 | 증적 원장(ev_ledger.tsv)의 실행 일련, 시험이면 회차와 시작 시각 |
| 7 | 증빙번호 범위 | EV-다섯 자리 범위. 폴더가 다르면 같은 번호도 다른 것이므로 대상ID·실행 일련과 함께 읽는다. 모르면 「확인 안 됨」 |
| 8 | 고친 판 | 고침이 들어간 판 번호. 고치지 않았으면 「없음」 |
| 9 | 재시험 일련 | 고친 뒤 같은 사례를 다시 돌린 실행 일련(J 단계). 아직 없으면 「없음」 |
| 10 | 상태 | 알려진 문제 · 원인 확인 안 됨 / 알려진 문제 · 원인 확인됨 / 재현 대상 / 재현됨 / 재현 안 됨 · 관찰 사례 / 종결. 원인이 확인되지 않았으면 「원인 확인 안 됨」을 그 글자 그대로 둔다. 「종결」은 결함 번호·증빙번호·재시험 일련이 채워진 뒤에만 |
| 11 | 요지 | 사건·결함·불편의 사실만. 개인정보·비밀 값 없이 |
| 12 | 근거 | 이력 번호 · 판정 번호 · 지시문 등 사실의 출처 |

- 칸 1~10은 Fable 지시문 0156 5절 길 1의 3항 순서 그대로이며, 11·12는 알려진 문제 줄을 읽을 수 있게 더했다.
- 지금 두 줄:
  1. 시험 가 1회차의 HiCoffer 종료와 USB 안내 되풀이(이력 1044). 원인 확인 안 됨.
  2. 시험 가 묶음 1.1의 변수 덮어쓰기(이력 1042 · 판정요청 114). 이력 1042에 원인이 확인되어 있어 「원인 확인됨(시험 묶음 결함)」으로 적었다. 지시문의 「원인 확인 안 됨」과 다른 점은 Fable에 알린다.
- 「결함 114」 표기 주의: SC-13 결함 대장의 #114는 2026-11-04 Haiku 지적(이력 114, GitHub 확인 지연)이며 묶음 결함과 무관하다. 지시문의 「결함 114」는 판정요청 114를 가리키는 것으로 읽어 결함 번호 칸에 「판정요청 114」로 적었다.
